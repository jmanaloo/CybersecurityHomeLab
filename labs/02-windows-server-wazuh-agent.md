# Lab 02 — Windows Server 2022 Deployment and Wazuh Agent Integration

**Date:** November 15, 2026  
**Project:** Cybersecurity Home Lab  
**Outcome:** Successfully installed Windows Server 2022, deployed the Wazuh agent, and confirmed the endpoint was **Active** in the Wazuh dashboard.

## Objective

Add a Windows Server 2022 endpoint to an existing Wazuh SIEM lab in VMware Workstation Pro. Verify VM-to-VM networking, diagnose blocked agent ports, install the Windows agent, and confirm successful enrollment.

> **Scope:** This lab starts with an existing, operational Wazuh Manager on Rocky Linux 9.5. It does not cover installing Wazuh from scratch. See [Lab 01](01-wazuh-installation.md) for the earlier troubleshooting session.

## Lab environment

| Component | Details |
|---|---|
| Hypervisor | VMware Workstation Pro |
| Wazuh server OS | Rocky Linux 9.5 |
| Wazuh Manager IP | `192.168.17.130` |
| Monitored endpoint | Windows Server 2022 (Desktop Experience) |
| Windows Server IP | `192.168.17.134` |
| Network | VMware NAT / VMnet8, `192.168.17.0/24` |
| Windows Server gateway | `192.168.17.2` |
| Windows agent installer | Wazuh agent `4.12.0-1` MSI, as generated by the lab dashboard |
| Agent name | `Win-serverlab` |

> **Note:** IP addresses were assigned in this lab and may differ after restarting the VMs. Replace them with your actual addresses when reproducing the steps.

## 1. Install Windows Server 2022 in VMware

1. Create or open the Windows Server virtual machine in VMware Workstation Pro.
2. With the VM powered off, open **VM > Settings > CD/DVD (SATA)**.
3. Select **Use ISO image file**, choose the Windows Server 2022 ISO, and enable **Connect at power on**.
4. Power on the VM. If the UEFI Boot Manager appears, choose **EFI VMware Virtual SATA CDROM Drive** and press a key when prompted.
5. Follow Windows Setup. For a GUI-based learning lab, select **Windows Server 2022 Standard (Desktop Experience)** if available and appropriately licensed.
6. Select **Custom installation** and the intended empty virtual disk. Set a strong Administrator password.
7. Log in and confirm **Server Manager** opens.

**Observed result:** Windows Server 2022 booted successfully and displayed Server Manager.

## 2. Identify the Windows Server network settings

Open **PowerShell** inside the Windows Server VM:

```powershell
ipconfig
```

**Observed configuration:**

```text
IPv4 Address . . . . . : 192.168.17.134
Subnet Mask  . . . . . : 255.255.255.0
Default Gateway . . . : 192.168.17.2
```

The Windows Server and Wazuh Manager were on the same VMware NAT subnet.

## 3. Verify IP connectivity to Wazuh

On **Windows Server PowerShell**:

```powershell
ping 192.168.17.130
```

**Observed result:** Four successful replies. Basic IP connectivity between the VMs worked.

## 4. Test Wazuh agent ports

On **Windows Server PowerShell**:

```powershell
Test-NetConnection 192.168.17.130 -Port 1514
Test-NetConnection 192.168.17.130 -Port 1515
```

| Port | Purpose | Initial test | After firewall change |
|---|---|---|---|
| `1514/TCP` | Agent-to-manager communication | `False` | `True` |
| `1515/TCP` | Agent enrollment | `False` | `True` |

A successful ping did **not** mean the application ports were reachable.

## 5. Diagnose the Wazuh Manager listener

Switch to the **Rocky Linux Wazuh VM** (not Windows Server). Check whether the manager is listening on TCP 1514:

```bash
ss -tlnp | grep ':1514'
```

**Observed result:** A listening socket was present for port 1514.

Check explicitly permitted firewall ports:

```bash
firewall-cmd --list-ports
```

**Observed result:** The port list was blank. This alone does not prove a port is blocked, because named firewall services can also allow traffic; combined with the connection tests, the firewall was the leading cause.

## 6. Allow Wazuh traffic through Rocky Linux firewalld

Run on the **Wazuh VM as root**. These rules were used in the isolated VMware lab:

```bash
firewall-cmd --permanent --zone=public --add-port=1514/tcp
firewall-cmd --reload
```

Then retest port 1514 from Windows Server:

```powershell
Test-NetConnection 192.168.17.130 -Port 1514
```

**Observed result:** `TcpTestSucceeded : True`.

Repeat for the enrollment port on the Wazuh VM:

```bash
firewall-cmd --permanent --zone=public --add-port=1515/tcp
firewall-cmd --reload
```

Retest from Windows Server:

```powershell
Test-NetConnection 192.168.17.130 -Port 1515
```

**Observed result:** `TcpTestSucceeded : True`.

Optional verification on Rocky Linux:

```bash
firewall-cmd --zone=public --list-ports
```

**Security note:** Opening these ports in the `public` zone can permit access from any reachable source. These broad rules were used for an isolated lab; in a shared or production network, restrict permitted sources to trusted endpoints and review the firewall zone configuration. Never expose Wazuh enrollment ports directly to the internet.

## 7. Generate the Windows agent installation command

In the Wazuh dashboard (`https://192.168.17.130`):

1. Open **Deploy new agent**.
2. Choose **Windows > MSI 32/64 bits**.
3. Enter manager address `192.168.17.130`.
4. Set the unique agent name to `Win-serverlab`.
5. Leave the agent group at `default`.
6. Copy the generated PowerShell installation command.

The lab dashboard generated an MSI download for **Wazuh agent 4.12.0-1** from `packages.wazuh.com`. The command used `Invoke-WebRequest` to download the package and `msiexec.exe` to install it with the `WAZUH_MANAGER` and `WAZUH_AGENT_NAME` properties.

**Reproducible example** (run in **Windows Server PowerShell as Administrator**; check the dashboard for the installer version appropriate to your environment):

```powershell
Invoke-WebRequest -Uri 'https://packages.wazuh.com/4.x/windows/wazuh-agent-4.12.0-1.msi' -OutFile "$env:TEMP\wazuh-agent.msi"
msiexec.exe /i "$env:TEMP\wazuh-agent.msi" /q WAZUH_MANAGER="192.168.17.130" WAZUH_AGENT_NAME="Win-serverlab"
```

`/q` requests a quiet MSI installation, so there may be no visible installer window. Allow the process to complete before checking the service.

## 8. Verify and start the Windows agent

On **Windows Server PowerShell (Administrator)**:

```powershell
Get-Service WazuhSvc
```

**Observed result:** The service existed and initially showed `Stopped`.

Start the service:

```powershell
Start-Service WazuhSvc
```

Check again:

```powershell
Get-Service WazuhSvc
```

**Observed result:** `Running`.

## 9. Confirm enrollment in the Wazuh dashboard

1. Open the Wazuh dashboard on the Windows host.
2. Navigate to the agents summary or agent management view.
3. Find `Win-serverlab`.
4. Verify that its status is **Active**.

**Observed result:** The Windows Server agent appeared as **Active**, confirming successful enrollment and communication with the manager.

## Troubleshooting summary

| Symptom | Investigation | Resolution |
|---|---|---|
| Windows Server could ping Wazuh, but TCP 1514 failed | Tested with `Test-NetConnection`; checked listener with `ss`; reviewed firewalld ports | Allowed `1514/tcp`, reloaded firewalld, retested |
| TCP 1515 failed | Repeated TCP connectivity test | Allowed `1515/tcp`, reloaded firewalld, retested |
| Agent service initially showed `Stopped` | `Get-Service WazuhSvc` | `Start-Service WazuhSvc` |
| Needed to verify agent-to-SIEM integration | Checked agent list in Wazuh dashboard | Confirmed **Active** status |

## Key lessons learned

- Two VMs on the same subnet can still have application traffic blocked by a firewall.
- `ping` tests ICMP reachability; `Test-NetConnection -Port` tests TCP reachability.
- `ss` helps identify listening services on Linux.
- `firewall-cmd --permanent` saves a rule; `firewall-cmd --reload` applies the saved configuration.
- Windows services can be inspected with `Get-Service` and started with `Start-Service`.
- A running Windows service and an **Active** Wazuh agent are separate verification checkpoints.
- Repeating a known troubleshooting workflow helped resolve the second blocked port more independently.
